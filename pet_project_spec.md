Ты — senior-аналитик данных и Python-разработчик. Твоя задача — создать с нуля публичный GitHub-репозиторий с аналитическим проектом. Они оценивают три вещи: умение задать бизнес-вопрос и ответить на него данными, чистоту кода на Python и SQL, понятность выводов.

## 1. Главные правила

1. **Только реальные цифры.** Все числа в README, отчете и выводах должны получаться из кода на реальных данных. Запрещено вписывать числа вручную, округлять «для красоты» или подгонять результат под ожидание. Если гипотеза не подтвердилась, так и пиши.
2. **Воспроизводимость.** Весь проект с нуля запускается одной командой `make all` на чистой машине после установки зависимостей и загрузки данных.
3. **Логика в модулях, не в ноутбуке.** Все вычисления лежат в пакете `src/retail_analysis/` и в файлах `sql/`. Ноутбук только вызывает функции, показывает таблицы и графики и содержит текст выводов.
4. **Данные не коммитятся.** Сырые и промежуточные данные лежат в `data/`, которая добавлена в `.gitignore`. В репозитории есть скрипт загрузки.
5. **Без лишнего.** Никаких неиспользуемых функций, закомментированного кода, отладочных `print`, файлов-заглушек и TODO в финальной версии.

## 2. Данные

**Датасет:** dunnhumby «The Complete Journey» — открытые данные о покупках около 2 500 домохозяйств в сети супермаркетов за 2 года (711 дней, 102 недели).

**Источник:** Kaggle, датасет `frtgnn/dunnhumby-the-complete-journey`. Загрузка через Kaggle API (`kaggle datasets download`). Токен Kaggle берется из стандартного `~/.kaggle/kaggle.json`, в репозиторий не попадает.

**Используемые таблицы:**

| Файл | Содержимое | Используется для |
|---|---|---|
| `transaction_data.csv` | ~2.6 млн строк позиций чеков: `household_key`, `BASKET_ID`, `DAY`, `PRODUCT_ID`, `QUANTITY`, `SALES_VALUE`, `STORE_ID`, `RETAIL_DISC`, `COUPON_DISC`, `WEEK_NO` и др. | все анализы |
| `product.csv` | справочник товаров: `DEPARTMENT`, `COMMODITY_DESC`, `SUB_COMMODITY_DESC`, `BRAND` | категории, каннибализация |
| `hh_demographic.csv` | демография части домохозяйств | описание сегментов |
| `causal_data.csv` | ~36 млн строк: размещение товара в каталоге (`mailer`) и выкладке (`display`) по магазину и неделе | оценка эффекта промо |

**Особенности, которые нужно учесть и описать в README:**
- Календарных дат нет, время задано номером дня `DAY` (1–711) и недели `WEEK_NO` (1–102). Работай в неделях.
- Выручка — `SALES_VALUE`. Строки с `QUANTITY = 0` или `SALES_VALUE <= 0` исключаются, их доля выводится в лог.
- Чек — уникальный `BASKET_ID`.
- Первые недели данных могут быть неполными. Проверь число активных домохозяйств по неделям и, если начало выборки неполное, обоснованно отрежь его, указав это в README.

## 3. Бизнес-вопросы

Проект отвечает ровно на четыре вопроса. Каждый вопрос — отдельный раздел отчета.

1. **Как устроен бизнес?** Недельная динамика выручки, числа чеков, активных клиентов и среднего чека. Топ категорий (`DEPARTMENT`, `COMMODITY_DESC`) по выручке и их доли.
2. **Какие есть клиентские сегменты?** RFM-сегментация домохозяйств и доля выручки каждого сегмента.
3. **Как удерживаются клиенты?** Когортный анализ удержания по неделе первой покупки.
4. **Работают ли промоакции?** Оценка прироста продаж от размещения товара в каталоге (`mailer`) методом difference-in-differences и проверка каннибализации соседних товаров той же подкатегории.

Отдельный вывод: **уходящие лояльные клиенты** — сколько их, какую долю выручки они давали и чем отличаются.

## 6. Этапы и требования к каждому

### 6.1. Загрузка (`download.py`)
- Скачивает и распаковывает датасет в `data/raw/`.
- Если файлы уже есть, повторно не скачивает.
- Если нет Kaggle-токена, падает с понятным сообщением, как его получить.

### 6.2. Подготовка (`prepare.py`, PySpark)
- Читает CSV с явно заданной схемой, а не через `inferSchema`.
- Приводит названия колонок к `snake_case`.
- Удаляет полные дубликаты и некорректные строки (раздел 2), считает и логирует, сколько строк удалено и почему.
- Сохраняет таблицы в `data/processed/` в Parquet. `causal_data` партиционируется по `week_no`.

### 6.3. Качество данных (`quality.py`)
Проверки, результат которых выводится в лог и в отчет:
- нет пропусков в ключевых полях;
- каждый `product_id` из транзакций есть в справочнике товаров;
- `week_no` в диапазоне 1–102;
- число активных домохозяйств по неделям (для решения об отрезании начала выборки).

Проверка с критической ошибкой останавливает пайплайн с понятным сообщением.

### 6.4. SQL-запросы (`sql/`)
- Каждый файл — один запрос с комментарием в начале: какой вопрос он решает и что возвращает.
- Обязательно использовать CTE и оконные функции там, где они естественны: `NTILE` для RFM, `MIN() OVER` или `ROW_NUMBER` для первой покупки в когортах, `LAG` для изменения активности. Это демонстрация навыков, но без искусственного усложнения.
- Ключевые слова SQL в верхнем регистре, одна колонка на строку в `SELECT`, осмысленные алиасы.
- Пути к Parquet и параметры подставляются из `config.yaml`, в SQL не хардкодятся.

### 6.5. RFM (`sql/03_rfm.sql`, `rfm.py`)
- Recency — недель с последней покупки до конца периода, Frequency — число чеков, Monetary — выручка.
- Баллы 1–5 по квинтилям через `NTILE(5)`.
- 5–7 понятных сегментов с бизнес-названиями (например, «Чемпионы», «Лояльные», «Под угрозой ухода», «Спящие», «Новые»). Правила сегментов описаны в `config.yaml` и в README.
- Результат: таблица сегментов с числом клиентов, средним чеком, частотой и долей выручки.

### 6.6. Когорты (`sql/04_cohorts.sql`, `cohorts.py`)
- Когорта — неделя первой покупки, сгруппированная в 4-недельные периоды.
- Матрица удержания: доля клиентов когорты, совершивших покупку в каждый следующий период.
- Тепловая карта и линейный график удержания нескольких когорт.

### 6.7. Уходящие лояльные (`sql/05_churning_loyal.sql`)
- Определение задается в `config.yaml` и описывается в README. Например: клиент входит в верхние 20% по выручке за первую половину периода, а в последние 12 недель его число чеков упало более чем на 50% относительно его же средней активности.
- Посчитай размер группы, ее долю в выручке и чем она отличается от остальных лояльных (категории, средний чек, демография, если есть).

### 6.8. Эффект промо (`promo.py`)
- **Воздействие:** товар размещен в каталоге (`mailer` не пустой) в конкретной неделе.
- **Контроль:** товары той же подкатегории (`SUB_COMMODITY_DESC`), которые не были в каталоге в окне анализа.
- **Окно:** 4 недели до и неделя промо (параметры в `config.yaml`).
- **Модель:** регрессия продаж на `treated * post` с фиксированными эффектами товара и недели, стандартные ошибки кластеризованы по товару (statsmodels). Результат — оценка эффекта, доверительный интервал и p-value.
- **Проверка параллельных трендов:** график средних продаж групп до промо и event-study-оценки по неделям до промо. Если тренды явно расходятся, это прямо пишется в выводах как ограничение.
- **Каннибализация:** изменение продаж непромо-товаров той же подкатегории в неделю промо, той же методикой. Вывод формулируется строго по результату, без заранее заданного ответа.
- Отдельный раздел ограничений: нет данных о цене до скидки по всем товарам, промо назначается не случайно, возможны другие одновременные акции.

### 6.9. Результаты (`reports/results.json`)
Пайплайн сохраняет в JSON все ключевые числа, которые упоминаются в README и отчете: число строк, клиентов и чеков, доли сегментов, удержание, размер и долю выручки уходящих лояльных, оценку эффекта промо с интервалом. README и отчет ссылаются только на эти числа.

## 7. Требования к коду

- Аннотации типов во всех публичных функциях.
- Docstring в стиле Google для каждой публичной функции: что делает, аргументы, что возвращает.
- Функции короткие и делают одно действие. Чистые функции расчетов отделены от ввода-вывода.
- Никаких магических чисел: пороги и параметры только из `config.yaml`.
- Пути через `pathlib`, без абсолютных путей.
- `logging` вместо `print`, уровень INFO по умолчанию.
- `ruff check` и `ruff format --check` проходят без ошибок.
- Имена переменных и функций на английском, комментарии и docstrings на английском, текст отчета и README на русском.

### Тесты
- Тесты работают на маленьких синтетических таблицах из `conftest.py`, без загрузки реальных данных и без Spark.
- Покрыть: расчет RFM-баллов и назначение сегментов, построение матрицы удержания (известный ответ на ручном примере), DiD на синтетических данных с заранее заданным эффектом (оценка должна его восстановить в пределах допуска), проверки качества данных.
- `pytest` проходит полностью.

## 8. Требования к графикам (`plots.py`)

- Единый стиль для всех графиков задается в одной функции.
- У каждого графика есть заголовок, сформулированный как вывод, а не как описание. Например: «Треть выручки приносят 10% клиентов», а не «Распределение выручки по клиентам».
- Подписаны оси и единицы измерения, проценты выводятся в процентах.
- Не больше 6 цветов на графике, без 3D и круговых диаграмм с множеством секторов.
- Графики сохраняются в `reports/figures/` в PNG, 150 dpi.
